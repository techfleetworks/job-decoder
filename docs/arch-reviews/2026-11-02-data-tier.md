# Architecture review: framework data tier and snapshot build (T11)

- Date: 2026-11-02
- Change: `feat/data-tier` (base `main`)
- Standard: `decisions.md`, ADR-0006, ADR-0008, ADR-0022, ADR-0027
- Review context: fresh (general-purpose subagent, not the authoring context)
- Verdict: **4 findings (2 med, 2 low), all fixed in this change**; mechanical gate PASS

## Scope

The T11 data tier: the `spf_release`/`spf_record` migration, the build-time pipeline
(`pipeline/lib/{manifest,relations,hash,integrity,supabase,release-source,derive}.mjs`,
`pipeline/sync-framework.mjs`, `pipeline/build-snapshot.mjs`), the eval harness refactor
to reuse the shared derivation, the data-tier BDD feature and steps, and the Vitest
discriminating tests. 13 code and schema files reviewed against the four questions, every
cell verdicted with evidence.

## What the review confirmed

- The read-model derivation has exactly one home (`pipeline/lib/relations.mjs`) and the
  eval harness imports it; there is no second copy to drift.
- `spf_release`/`spf_record` have a single writer (the sync step), and the one-published
  invariant is enforced in the database by a partial unique index, not in app code. The
  `(release, entity, slug)` primary key makes "resolve by (entity, slug)" a real key.
- The snapshot is derived from the release, not hand-copied; items live once in
  `items.json` and are referenced by slug, not duplicated into each slice.
- RLS is deny-by-default on both tables, asserted by a BDD scenario. The service-role
  client is imported lazily and only in tier-2 tooling, never bundled into the browser.
- Every Supabase call checks its error and throws loudly; no empty catches; a half-written
  release is left as a draft, never published.

## Findings (all fixed in this change)

- **F1 (med, error-handling):** `loadAliases` in `build-snapshot.mjs` and
  `eval/lib/framework.mjs` caught every error and returned `{}`, so a corrupt committed
  `aliases.json` would silently ship a snapshot with zero aliases and lose matcher recall.
  **Fixed:** a missing file still recovers to `{}`, but a parse error now throws and fails
  the build closed.
- **F2 (med, dependency-direction):** `pipeline/lib/relations.mjs` and `derive.mjs`
  imported `normalize` from `eval/lib/text.mjs`, so the declared derivation owner depended
  on the dev eval harness (a reversed, folder-level coupling). **Fixed:** the text
  primitives moved to `pipeline/lib/text.mjs` (the owner side); `eval/lib/text.mjs`
  re-exports them, so eval callers are unchanged and the back-edge is gone.
- **F3 (low, data-ownership):** `supabaseRelease` returned the stored `content_hash`
  without recomputing it over the rows read, so a record changed without a re-sync could
  ship under a stale, lying pin. **Fixed:** the hash is recomputed over the rows read and
  the build fails closed on a mismatch, matching the record-count check.
- **F4 (low, over-engineering):** `entityByName` was dead code, exported and re-exported
  with no caller. **Fixed:** removed.

## Verification

After the fixes, on this branch: architecture gate PASS, `tsc --noEmit` clean, Vitest
suite green (28 tests), `next lint` clean, `next build` succeeds, all BDD and snapshot
gates pass, and the local snapshot still builds to content hash `c0917a7135f4f03a`. The
eval harness still loads (221 items, titles resolve) after the text-module move. The
machine-readable record is appended to `docs/arch-reviews/log.jsonl`.

## Limitation

The `supabaseRelease` hash re-verification (F3) assumes the records round-trip through
JSONB to the same canonical hash. The Supabase read path is not wired into the live build
yet (ADR-0027), so this is validated when that path is first brought up; a mismatch there
is a loud, fixable signal, which is the intended fail-closed behavior.
