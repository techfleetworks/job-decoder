# ADR-0038: WCAG 2.2 AA conformance pass and the focus-management pattern

- Status: Accepted
- Date: 2026-11-03
- Deciders: Morgan (mdenner@techfleet.org)
- Builds on: [ADR-0013](0013-ui-design-system-and-rules.md) (UI rules, contrast, target size), [ADR-0023](0023-show-all-evidence-per-hat.md) (results stepper and receipt).

## Context

T14 is the accessibility item, sequenced last in MVP1 by Morgan's decision. The automated layer
already existed (axe component tests via `jest-axe`, `eslint-plugin-jsx-a11y`), but automated
tools catch only a third to a half of accessibility issues. The remaining criteria, above all
keyboard operability and focus management on this app's view transitions, needed a manual pass
against WCAG 2.2 AA, recorded criterion by criterion.

The app is a single-page flow that swaps whole screens in place (input → results → prep) and
steps within the results and prep screens. Every such swap unmounts the focused control, so
without explicit focus management, focus falls to `<body>` and a screen-reader or keyboard user
is not told the screen changed and loses their place.

A manual pass was run on the deployed app by keyboard-only operation and accessibility-tree
inspection (names, roles, states, live regions), plus computed contrast, target sizes, and
reflow. The full ledger is in `docs/accessibility/wcag-2.2-aa-conformance.md`.

## Decision

1. **Every view transition moves focus to the new screen's heading.** Results already focused
   its verdict heading on mount and each step heading on change. Extend the same pattern to the
   two places that were dropping focus to `<body>`: PrepView focuses its heading on entry, and
   returning to the input form moves focus to its heading. The form does **not** grab focus on
   first page load (focus starts at the top of the document there); it only does so when the
   user returns from a result, gated by a "a decode has happened" ref in the flow.

2. **Dynamic status is announced in live regions, never only on screen.** The working state and
   the copy-button result each render in a visually hidden `role="status"` region, and a failed
   clipboard reports the manual-selection fallback to the user rather than logging only to the
   console.

3. **The dialog keeps MUI's focus trap and return, with `aria-modal` added** so assistive tech
   treats the background as inert, matching the ARIA dialog pattern.

4. **Conformance is recorded, not asserted.** A committed conformance record gives every
   applicable WCAG 2.2 A/AA criterion a verdict with a re-runnable source, so "it is accessible"
   is item by item, not a vibe. Meeting WCAG 2.2 A/AA also satisfies Section 508 and the ADA
   Title II web standard, which it is a superset of.

## Consequences

- Focus management is consistent across every screen and step, so a keyboard or screen-reader
  user always hears the new screen and keeps their place. Component tests assert the focus moves
  (PrepView and InputForm) so a regression fails CI.
- The pattern is now a rule: any new screen or view swap must move focus to its heading on
  entry. A new screen that does not is an accessibility regression.
- **Honest limits:**
  - The manual pass used keyboard + accessibility-tree evidence, which exposes the names, roles,
    states, and live regions a screen reader uses, but it is **not** an audio screen-reader pass.
    Running one real reader (NVDA/JAWS/VoiceOver/TalkBack) across the flow is the one remaining
    verdict, tracked in the conformance record.
  - 1.4.10 Reflow was verified by "no horizontal overflow" at the tested widths and a fluid
    single-column layout; a dedicated 320px-viewport emulation is a recommended repeat.
  - The conformance record is a manual ledger; this repo does not (yet) install the
    `check-a11y-checklist` gate that would fail CI on an un-verdicted criterion. Adding it is a
    possible follow-up; today the axe component tests are the automated gate in CI.

## Alternatives considered

- **Manage focus centrally in DecodeFlow instead of per screen.** Rejected: each screen already
  owns its own heading and mount effect; a central focus controller would have to reach into
  each child's heading ref, coupling the flow to every screen's internals. Per-screen focus on
  mount keeps each screen self-contained.
- **Auto-focus the form on every mount, including first load.** Rejected: moving focus on
  initial page load is disorienting and unnecessary (focus already starts at the top). Focus is
  moved only when returning from a result.
- **Rely on the axe automated pass alone.** Rejected: axe does not catch focus-management loss
  on a view swap (both PrepView and the form passed axe while dropping focus to `<body>`), which
  is exactly why the manual pass exists.
